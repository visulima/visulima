# Amazon S3

> **Just need ad-hoc uploads?** Wrap this adapter in the [`Files` facade](../files-facade.mdx) for a one-liner API. The reference below shows direct adapter usage — pick that path when you're hosting an upload server (TUS / multipart / REST handlers, lifecycle hooks, transformers).

## Overview

`S3Storage` stores uploads in an Amazon S3 bucket through the official AWS SDK v3. Every upload is an S3 multipart upload: `create()` starts it, each `write()` appends one part, and the last part completes it. The same adapter talks to any S3-compatible service (R2, MinIO, Spaces, Wasabi, …) through the [client helpers](#s3-compatible-services).

### S3Storage or AwsLightStorage?

| Need                                                    | Use                                  |
| ------------------------------------------------------- | ------------------------------------ |
| Node.js server, AWS credential chain (SSO, IAM role, …) | `S3Storage`                          |
| Presigned read/upload URLs (`files.url()`, signed PUT)  | `S3Storage`                          |
| `clientDirectUpload` (browser uploads parts to S3)      | `S3Storage`                          |
| Edge / worker runtime, no AWS SDK in the bundle         | [`AwsLightStorage`](./aws-light.mdx) |
| Bun with its built-in S3 client                         | [`BunS3Storage`](./bun-s3.mdx)       |

Both S3 adapters share the same upload logic (`S3BaseStorage`), so uploads, metadata records and limits behave the same.

## Provider setup

### 1. Create the bucket

```sh
aws s3api create-bucket --bucket my-uploads --region eu-central-1 \
  --create-bucket-configuration LocationConstraint=eu-central-1
```

Keep **Block Public Access** on unless you deliberately serve objects publicly; the adapter reads private objects with signed requests and hands out presigned URLs.

### 2. Grant the minimum IAM permissions

Attach this policy to the IAM user or role the server runs as (replace `my-uploads`):

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "Bucket",
            "Effect": "Allow",
            "Action": ["s3:ListBucket", "s3:ListBucketMultipartUploads"],
            "Resource": "arn:aws:s3:::my-uploads"
        },
        {
            "Sid": "Objects",
            "Effect": "Allow",
            "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts"],
            "Resource": "arn:aws:s3:::my-uploads/*"
        }
    ]
}
```

| Permission                      | Used for                                                                                                                                                                                      |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `s3:ListBucket`                 | The startup bucket check (`HeadBucket`), `list()` / `listDirectory()` (`ListObjectsV2`). **Also required so a missing key answers 404**: without it S3 answers `403` for every absent object. |
| `s3:ListBucketMultipartUploads` | `purge()` — finding expired, unfinished multipart uploads                                                                                                                                     |
| `s3:PutObject`                  | `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, the destination of `copy()`/`move()`, metadata records, presigned `PUT` URLs                                                |
| `s3:GetObject`                  | `get()`, `getStream()`, `HeadObject` (`exists()`, metadata reads), the source of `copy()`/`move()`, presigned `GET` URLs                                                                      |
| `s3:DeleteObject`               | `delete()`, `move()`, metadata cleanup                                                                                                                                                        |
| `s3:AbortMultipartUpload`       | Deleting/purging an unfinished upload                                                                                                                                                         |
| `s3:ListMultipartUploadParts`   | Resuming an upload (`ListParts` recomputes the offset)                                                                                                                                        |
| `s3:PutObjectAcl`               | Only when you set the `acl` option                                                                                                                                                            |

If the bucket uses SSE-KMS with a customer-managed key, also allow `kms:Encrypt`, `kms:Decrypt` and `kms:GenerateDataKey` on that key. If you keep metadata in a [separate bucket](#metadata-storage), grant the object permissions and `s3:ListBucket` on that bucket too.

### 3. CORS (only for browser-direct traffic)

Uploads that go through your server (the TUS / REST / multipart handlers) need no bucket CORS — the browser only talks to your server. You need a CORS rule when the browser talks **to S3 directly**:

- presigned `PUT` URLs from `storage.getUploadUrl()` / `files.signedUploadUrl()`,
- `clientDirectUpload: true` (the browser `PUT`s each part to a presigned `UploadPart` URL and must read the part's `ETag`),
- `fetch()`/XHR reads of presigned `GET` URLs from another origin (plain `<img>`/`<a>` tags need no CORS).

```json
{
    "CORSRules": [
        {
            "AllowedOrigins": ["https://app.example.com"],
            "AllowedMethods": ["GET", "HEAD", "PUT"],
            "AllowedHeaders": ["*"],
            "ExposeHeaders": ["ETag"],
            "MaxAgeSeconds": 3600
        }
    ]
}
```

```sh
aws s3api put-bucket-cors --bucket my-uploads --cors-configuration file://cors.json
```

### 4. Lifecycle rule for abandoned multipart uploads

An unfinished multipart upload is invisible in object listings but its parts are billed. The adapter's [`purge()`](#expiration-and-purge) only aborts uploads **it created and still has metadata for**; anything else (crashed clients of other tools, uploads whose metadata was lost, uploads with a custom `filename`) needs a bucket lifecycle rule:

```json
{
    "Rules": [
        {
            "ID": "abort-incomplete-multipart-uploads",
            "Status": "Enabled",
            "Filter": {},
            "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
        }
    ]
}
```

```sh
aws s3api put-bucket-lifecycle-configuration --bucket my-uploads --lifecycle-configuration file://lifecycle.json
```

Pick `DaysAfterInitiation` longer than the longest time a client may pause a resumable upload. Don't add an `Expiration` rule that matches `*.META` objects unless you also want the metadata of finished uploads to disappear.

## Configuration

`S3StorageOptions` is the [common storage options](#common-storage-options) + every [`S3ClientConfig`](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/Package/-aws-sdk-client-s3/Interface/S3ClientConfig/) field (passed straight to `new S3Client()`) + the S3-specific options below.

```ts
import { S3Storage } from "@visulima/storage/provider/aws";

// Bucket, region and credentials from S3_BUCKET, S3_REGION and the AWS credential chain
const storage = new S3Storage({});
```

### Production example

```ts
import { S3Storage } from "@visulima/storage/provider/aws";

const storage = new S3Storage({
    bucket: "my-uploads",
    region: "eu-central-1",
    // credentials omitted: the IAM role of the ECS task / EC2 instance / Lambda is used

    maxUploadSize: "2GB",
    allowMIME: ["image/*", "video/*", "application/pdf"],

    // Abandoned uploads are deleted after a day; checked every hour
    expiration: { maxAge: "24h", purgeInterval: "1h", rolling: true },

    retryConfig: { maxRetries: 5, initialDelay: 500 },
    defaultTimeout: 30_000,

    logger: console,
});
```

## Metadata storage

Every upload has a metadata record (id, name, size, offset, `UploadId`, user metadata, timestamps). Where it lives:

| Configuration                                          | Records stored in                                                       | Multiple server instances                  |
| ------------------------------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------ |
| default (no `metaStorage`, no `metaStorageConfig`)     | the same bucket, as zero-byte objects `<id>.META`                       | ✅ shared                                  |
| `metaStorageConfig: { bucket: "my-uploads-meta" }`     | another bucket (same region/credentials unless overridden), `<id>.META` | ✅ shared                                  |
| `metaStorageConfig: { directory: "/var/lib/uploads" }` | JSON files on the local disk                                            | ❌ unless the directory is a shared volume |
| `metaStorage: new MyMetaStorage()`                     | wherever your implementation puts them (Redis, SQL, …)                  | depends                                    |

`metaStorageConfig` also takes `prefix` (default `""`) and `suffix` (default `".META"`) to rename the records, e.g. `{ prefix: ".meta/" }` to keep them under one folder.

What this implies:

- **The record is kept after completion.** Finished uploads keep their `<id>.META` object; `get()`/`exists()` use it to find the object (its key differs from the id with a custom `filename`). It is removed by `delete()`, `move()` and `purge()`.
- **Records are hidden from `list()`.** Keys matching `prefix…suffix` are skipped, so the default `.META` objects never show up as files. Other tools listing the bucket do see them.
- **Size limit.** In the bucket the record is stored in the object's user-metadata header, which S3 caps at **2 KB**. Upload metadata is also copied onto the object itself (`x-amz-meta-*`). Keep client metadata small, or move records to a local directory / custom `metaStorage` if you need more.
- **Concurrent writers.** The bucket store uses conditional writes (`If-Match`), so chunked uploads hitting several instances merge their progress safely. Local directory storage locks across processes sharing the directory.
- **Lost metadata.** An object without a record (written by another tool, or completed by an older version) can still be read, copied and deleted by its key; `purge()` leaves it alone.

## Behaviour & limits

| Topic               | Behaviour                                                                                                                                                                                                                                                                    |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resumable / chunked | ✅ Supported, **sequential only** (`sequentialWrites: true`): every chunk must start where the upload ends. An out-of-order chunk is rejected with `409 FILE_CONFLICT` and the stored offset is corrected, so the client's next `HEAD` gets the real offset.                 |
| Chunk size          | Every chunk except the last must be **≥ 5 MiB** (S3 rejects smaller parts at completion; the adapter rejects them up front with `400`). At most 10,000 parts per upload — chunk size × 10,000 bounds the file size.                                                          |
| Checksums           | `md5` only (`Upload-Checksum` → `Content-MD5`, verified by S3; mismatch → `CHECKSUM_MISMATCH`). Other algorithms answer `UNSUPPORTED_CHECKSUM_ALGORITHM`.                                                                                                                    |
| Range reads         | ✅ `supportsRange`: `get()`/`getStream()`/`files.download({ range })` send an HTTP `Range` header.                                                                                                                                                                           |
| Read URLs           | ✅ `getReadUrl(key, { expiresIn, responseContentDisposition, responseContentType })` — presigned `GET`, default 3600 s, max 7 days (SigV4).                                                                                                                                  |
| Upload URLs         | ✅ `getUploadUrl(key, { contentType, contentLength, expiresIn })` — presigned single `PUT`, default 3600 s. The object is written by S3 directly: no metadata record, no hooks.                                                                                              |
| `list(limit)`       | Recursive listing of the whole bucket via `ListObjectsV2`, paged internally up to `limit` (default 1000). Returns object keys and `LastModified` only (no per-object `HEAD`). Includes objects this storage didn't create; excludes metadata records and unfinished uploads. |
| `listDirectory()`   | ✅ Native `Delimiter`/`Prefix` (`supportsDelimiter`), used by `files.list({ delimiter })`.                                                                                                                                                                                   |
| `copy()` / `move()` | Server-side `CopyObject` within the same bucket (optional `storageClass`); `move()` = copy + delete. The copy has no metadata record. `CopyObject` is limited to 5 GB by S3.                                                                                                 |
| `exists()`          | `HeadObject` on the upload's object; `false` only for a 404. An unfinished upload has no object yet, so it doesn't exist.                                                                                                                                                    |
| ACL                 | Only via `acl`; ignored for presigned URLs.                                                                                                                                                                                                                                  |

### Custom filename

`filename(file)` sets the object key; the id stays the upload id and the metadata record stays `<id>.META`. `get()`, `delete()` & co. resolve the key from the record. Two consequences:

- `list()` returns object keys (the custom names), not upload ids.
- `purge()` looks records up by object key, so with a custom `filename` it doesn't find them and **purges nothing** — rely on the S3 lifecycle rule above for unfinished uploads, and on your own cleanup for finished ones.

### Expiration and purge

With `expiration: { maxAge }`, an upload older than `maxAge` (from creation, or from its last write with `rolling: true`) answers `410 GONE` and is deleted. `purge()` (run every `purgeInterval`, or manually) deletes:

1. finished uploads whose object is older than `maxAge` **and** that have a metadata record — objects the storage didn't create are never touched;
2. unfinished multipart uploads older than `maxAge` whose `UploadId` matches a record of this storage. Other clients' multipart uploads in a shared bucket are left alone (use the lifecycle rule).

`purge()` inspects the first 1000 objects returned by `list()`; for larger buckets run your own cleanup or rely on lifecycle rules. The interval timer is `unref`'d; call `storage.close()` to stop it.

### Retries

Defaults: `maxRetries: 3`, `initialDelay: 1000`, `maxDelay: 30000`, `backoffMultiplier: 2` (exponential backoff with jitter). Retried: HTTP 408, 429, 500, 502, 503, 504, AWS server faults (`$fault: "server"`), errors the SDK marks retryable, and network errors. Aborted and timed-out calls are never retried. A `shouldRetry` you pass in `retryConfig` is asked first; returning `undefined` falls back to these defaults, and `retryableStatusCodes` replaces the status list. The AWS SDK's own retry (`maxAttempts`, part of `S3ClientConfig`) runs underneath.

### Direct uploads

With `clientDirectUpload: true` the server never sees the file bytes: `create()` (TUS `POST` / REST `POST`) starts the multipart upload and returns `partsUrls` — one presigned `UploadPart` URL per `partSize` chunk, valid for `expiration.maxAge` (default 6 h). The client `PUT`s each part to its URL, then calls the handler again (`PATCH`/`PUT` without a body) — the adapter lists the parts and completes the upload once their sizes add up to the file size. Requires the [CORS rule](#3-cors-only-for-browser-direct-traffic) with `ExposeHeaders: ["ETag"]`.

### Conditional requests

`S3Storage` sends the `Files` ETag predicates natively: `ifNoneMatch: "*"` / `ifMatch` uploads on `CompleteMultipartUpload`, exact reads on `GetObject`, `DeleteObject` with `If-Match`, and `CopyObject` with `x-amz-copy-source-if-match` plus a destination `If-None-Match` / `If-Match`. A 412 becomes `UploadError(ERRORS.PRECONDITION_FAILED)`; a failed conditional upload aborts its multipart upload and keeps the stored object's metadata record.

The claim is made for AWS only: with a custom `endpoint` (or `AWS_ENDPOINT_URL[_S3]` in the environment) every `capabilities.conditional` flag is `false`, because S3-compatible services differ in which of these headers they honour. Pass `conditional: true` when your service supports them, or `false` to opt out. `clientDirectUpload` disables conditional requests.

## S3-compatible services

Spread a client helper from `@visulima/storage/provider/aws/s3/clients` into the options; it sets `endpoint`, `region`, `credentials` (and `forcePathStyle` where needed):

```ts
import { S3Storage } from "@visulima/storage/provider/aws";
import { cloudflare } from "@visulima/storage/provider/aws/s3/clients";

const storage = new S3Storage({ bucket: "my-bucket", ...cloudflare() });
```

## Using it with the handlers

**Node (Express, `node:http`, …)**

```ts
import express from "express";
import { S3Storage } from "@visulima/storage/provider/aws";
import { Tus } from "@visulima/storage/handler/http/node";

const storage = new S3Storage({ bucket: "my-uploads", region: "eu-central-1" });
const tus = new Tus({ storage });

const app = express();

app.use("/files", tus.handle);
app.listen(3000);
```

**Fetch (Hono, Bun, Deno, Next.js route handlers, …)**

```ts
import { S3Storage } from "@visulima/storage/provider/aws";
import { Rest } from "@visulima/storage/handler/http/fetch";

const storage = new S3Storage({ bucket: "my-uploads", region: "eu-central-1" });
const rest = new Rest({ storage });

export const handler = (request: Request): Promise<Response> => rest.fetch(request);
```

Clients that upload in chunks (TUS, chunked REST) must send chunks of at least 5 MiB except for the last one — e.g. `chunkSize: 8 * 1024 * 1024` in `tus-js-client`.

**Files facade**

```ts
import { Files } from "@visulima/storage";
import { S3Storage } from "@visulima/storage/provider/aws";

const files = new Files({ adapter: new S3Storage({ bucket: "my-uploads", region: "eu-central-1" }) });

await files.upload("avatars/42.png", buffer, { contentType: "image/png" });

const url = await files.url("avatars/42.png", { expiresIn: 600 });
const { files: images, prefixes } = await files.list({ prefix: "avatars/", delimiter: "/" });
```

The raw `S3Client` is available as `storage.raw` for anything the adapter doesn't cover.

## Image transformations

Any adapter works with the [transformers](../transformers.mdx):

```ts
import ImageTransformer from "@visulima/storage/transformer/image";

const images = new ImageTransformer(storage, { maxImageSize: 10 * 1024 * 1024 });

const thumbnail = await images.resize("image.jpg", { width: 300, height: 200, fit: "cover" });
```

Presigned URLs return the original bytes; put a CDN (e.g. CloudFront) in front of your transform route to cache transformed variants.

## Troubleshooting

| Symptom                                                                        | Cause / fix                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `403 AccessDenied` for a file that doesn't exist (expected `404`)              | The role lacks `s3:ListBucket` on the bucket ARN; S3 then hides whether a key exists. Add it.                                                                                                                                |
| `403` on every request, or the startup check fails                             | Wrong credentials, policy on the wrong ARN (`arn:aws:s3:::bucket` for bucket actions, `arn:aws:s3:::bucket/*` for objects), or a missing KMS permission.                                                                     |
| `SignatureDoesNotMatch` / `AuthorizationHeaderMalformed` / `PermanentRedirect` | `region` doesn't match the bucket's region, or `endpoint` is wrong. Use the bucket's real region; for S3-compatible services use the client helper.                                                                          |
| Browser: "blocked by CORS policy" on a presigned URL or part `PUT`             | Add the bucket CORS rule for your origin and method; for direct multipart also expose `ETag`.                                                                                                                                |
| `409 FILE_CONFLICT` during chunked/TUS upload                                  | A chunk didn't start at the stored offset (parallel or out-of-order chunks). S3 uploads are sequential — upload chunks one at a time; on resume, `HEAD` first and continue from `Upload-Offset`.                             |
| `400 … chunks of at least 5 MiB`                                               | Client chunk size below 5 MiB. Raise it.                                                                                                                                                                                     |
| `400 MetadataTooLarge`                                                         | Upload metadata exceeds S3's 2 KB user-metadata limit. Send less metadata or use a local / custom metadata store.                                                                                                            |
| Storage charges for "invisible" data                                           | Unfinished multipart uploads. Add the `AbortIncompleteMultipartUpload` lifecycle rule and/or enable `expiration`.                                                                                                            |
| Handler answers `Storage initialization timeout`                               | The startup bucket check (`HeadBucket`, waits up to 30 s for the bucket) hasn't succeeded; handlers wait 5 s for it per request and retry it on the next one. Check the bucket name, region, credentials and network access. |
| `AccessControlListNotSupported`                                                | `acl` is set but the bucket has ACLs disabled (Object Ownership "Bucket owner enforced"). Drop `acl` or enable ACLs.                                                                                                         |
