# Caching

Two parts of the package accept a cache: the storage adapters (`cache` option) and the media transformers (`cache` / `cacheTtl`). Only the transformers read from their cache. Any object with the shape below works; `LRUCache` from `lru-cache` already has it.

## Cache interface

The package does not export a `Cache` type. A cache is any object with these methods (sync or async):

```typescript
interface Cache<K = string, V = unknown> {
    get(key: K): V | undefined | Promise<V | undefined>;
    set(key: K, value: V, options?: { ttl?: number }): boolean | Promise<boolean>;
    delete(key: K): boolean | Promise<boolean>;
    clear(): void | Promise<void>;
    has(key: K): boolean | Promise<boolean>;
    /** Optional. Lets transformers evict every cached variant of one file; without it `clear()` is used. */
    keys?(): Iterable<K>;
}
```

## Transformer caching

Transformers cache their results by file id plus transformation parameters, so a repeated request for the same variant is served from the cache instead of being re-encoded:

```typescript
import { MediaTransformer } from "@visulima/storage/transformer";
import ImageTransformer from "@visulima/storage/transformer/image";
import VideoTransformer from "@visulima/storage/transformer/video";
import { LRUCache } from "lru-cache";

const transformer = new MediaTransformer(storage, {
    cache: new LRUCache({ max: 100, ttl: 3_600_000 }),
    cacheTtl: 3600, // seconds
    ImageTransformer,
    VideoTransformer,
});
```

`ImageTransformer`, `VideoTransformer` and `AudioTransformer` accept the same `cache` / `cacheTtl` options when you use them directly. Clear the cached variants of a file after it changes with the transformer's `clearCache(fileId)`; it uses `keys()` when the cache has it and falls back to `clear()` otherwise.

## Storage adapter `cache` option

```typescript
import { DiskStorage } from "@visulima/storage";
import { LRUCache } from "lru-cache";

const storage = new DiskStorage({
    directory: "./uploads",
    cache: new LRUCache({ max: 1000, ttl: 3_600_000 }),
});
```

The adapter **writes** file metadata into this cache (on save and on `getMeta`) and removes the entry when metadata is deleted, but it never **reads** from it: every `getMeta` / `head` / `get` still goes to the meta storage and the backend. The option does not reduce API calls. Use it only if your own code wants to look up recently seen `File` records by id (`storage.cache.get(id)`). Leave it unset otherwise; the default is a no-op cache.

## Using Redis or another shared store

Wrap the client in an object with the interface above:

```typescript
import { Redis } from "ioredis";

const redis = new Redis();

const redisCache = {
    async get(key: string) {
        const value = await redis.get(key);

        return value ? JSON.parse(value) : undefined;
    },
    async set(key: string, value: unknown, options?: { ttl?: number }) {
        await (options?.ttl ? redis.set(key, JSON.stringify(value), "PX", options.ttl) : redis.set(key, JSON.stringify(value)));

        return true;
    },
    async delete(key: string) {
        return (await redis.del(key)) > 0;
    },
    async clear() {
        // Scope this to your own key prefix in production; flushdb wipes the whole database.
        await redis.flushdb();
    },
    async has(key: string) {
        return (await redis.exists(key)) === 1;
    },
};
```

Transformer results contain binary buffers, so a JSON-serialising cache like this one suits metadata better than transformed media. For media, prefer an in-process `LRUCache` with a `max` / `maxSize` limit.
