# TUS Handler

The TUS (Tus Resumable Upload Protocol) handler provides resumable uploads for large files, unreliable networks, and scenarios where uploads may be interrupted.

## Overview

TUS is an open protocol for resumable file uploads. It allows clients to:

- Resume interrupted uploads
- Upload large files efficiently
- Track upload progress
- Handle network failures gracefully

## Installation

TUS handler is included in the main package - no additional installation required.

## Basic Usage

### Express

```typescript
import express from "express";
import { DiskStorage } from "@visulima/storage";
import { Tus } from "@visulima/storage/handler/http/node";

const app = express();
const storage = new DiskStorage({ directory: "./uploads" });
const tus = new Tus({ storage });

// TUS endpoints
app.post("/upload/tus", tus.handle);
app.patch("/upload/tus/:id", tus.handle);
app.head("/upload/tus/:id", tus.handle);
app.delete("/upload/tus/:id", tus.handle);
```

### Modern Frameworks (Fetch API)

```typescript
import { DiskStorage } from "@visulima/storage";
import { Tus } from "@visulima/storage/handler/http/fetch";

const storage = new DiskStorage({ directory: "./uploads" });
const tus = new Tus({ storage });

// TUS endpoints
app.post("/upload/tus", async (c) => {
    return await tus.fetch(c.req.raw);
});

app.patch("/upload/tus/:id", async (c) => {
    return await tus.fetch(c.req.raw);
});

app.head("/upload/tus/:id", async (c) => {
    return await tus.fetch(c.req.raw);
});

app.delete("/upload/tus/:id", async (c) => {
    return await tus.fetch(c.req.raw);
});
```

## Client-Side Usage

### JavaScript/TypeScript

```typescript
import * as tus from "tus-js-client";

const file = document.getElementById("file-input").files[0];

const upload = new tus.Upload(file, {
    endpoint: "http://localhost:3000/upload/tus",
    retryDelays: [0, 3000, 5000, 10000, 20000],
    metadata: {
        filename: file.name,
        filetype: file.type,
    },
    onError: (error) => {
        console.error("Upload failed:", error);
    },
    onProgress: (bytesUploaded, bytesTotal) => {
        const percentage = ((bytesUploaded / bytesTotal) * 100).toFixed(2);
        console.log(`Upload progress: ${percentage}%`);
    },
    onSuccess: () => {
        console.log("Upload finished:", upload.url);
    },
});

// Start the upload
upload.start();

// Pause the upload
upload.abort();

// Resume the upload
upload.start();
```

## TUS Extensions

The TUS handler supports several extensions:

### Creation Extension

Create uploads with metadata:

```typescript
// POST /upload/tus
// Headers:
//   Upload-Length: 10485760
//   Upload-Metadata: filename dGVzdC5qcGc=,filetype aW1hZ2UvanBlZw==
```

### Creation-with-Upload Extension

Create and upload in a single request:

```typescript
// POST /upload/tus
// Headers:
//   Upload-Length: 10485760
//   Content-Type: application/offset+octet-stream
// Body: [file data]
```

### Termination Extension

Delete incomplete uploads:

```typescript
// DELETE /upload/tus/:id
```

### Creation-Defer-Length Extension

Start an upload before its size is known, and send `Upload-Length` with a later `PATCH`. The value is
checked against `maxUploadSize` (413), and an `Upload-Defer-Length` other than `1` is rejected with 400.

```typescript
// POST /upload/tus
// Headers:
//   Upload-Defer-Length: 1

// PATCH /upload/tus/:id
// Headers:
//   Upload-Offset: 0
//   Upload-Length: 10485760
```

### Checksum Extension

Verify each chunk. The checksum is the **base64** digest of the chunk's bytes:

```typescript
// PATCH /upload/tus/:id
// Headers:
//   Upload-Offset: 0
//   Upload-Checksum: sha1 qvTGHdzF6KLavt4PO0gs2a6pQ00=   (SHA-1 of the bytes "hello")
//   Content-Type: application/offset+octet-stream
// Body: [chunk data]
```

`Tus-Checksum-Algorithm` lists the algorithms the storage adapter verifies natively, followed by the ones the
handler verifies itself (`md5`, `sha1`, `sha256`, `sha384`, `sha512`). When the handler verifies a checksum, it
buffers that chunk in memory first, so keep chunks for checksummed uploads at a sensible size. A mismatch is
answered with `460 Checksum Mismatch` and the chunk is discarded; an unknown algorithm gets `400`.

### Concatenation Extension

Upload parts in parallel as partial uploads and join them with a final upload. Partial uploads are referenced
by their URLs (absolute or relative); bare upload IDs are accepted too. A finished partial upload is not
processed on its own: `onComplete` and the `completed` event fire for the final upload only.

```typescript
// POST /upload/tus            Upload-Concat: partial          → Location: /upload/tus/a
// POST /upload/tus            Upload-Concat: partial          → Location: /upload/tus/b
// POST /upload/tus            Upload-Concat: final;/upload/tus/a /upload/tus/b
```

### X-HTTP-Method-Override

Clients behind proxies that only allow `GET`/`POST` can send the real method in `X-HTTP-Method-Override`; the
handler uses it in place of the request method, as the protocol requires.

### Expiration Extension

Automatic cleanup of expired uploads:

```typescript
const storage = new DiskStorage({
    directory: "./uploads",
    expiration: {
        maxAge: "24h",
        purgeInterval: "1h",
    },
});
```

## Response Headers

TUS responses include standard TUS headers:

- `Tus-Resumable`: TUS protocol version (e.g., "1.0.0")
- `Tus-Version`: Supported TUS versions
- `Tus-Extension`: Supported TUS extensions
- `Tus-Max-Size`: Maximum upload size
- `Location`: Upload URL for created uploads
- `Upload-Offset`: Current upload offset
- `Upload-Expires`: Upload expiration timestamp

## Storage Backend Limits

Resumable, chunked TUS uploads need a backend that can append to an upload:

- **Disk, Memory, S3 (incl. aws-light), GCS and Azure** support chunked uploads. S3 needs every chunk except the
  last to be at least 5 MiB; a smaller chunk is rejected right away with `400`.
- **Box, Bunny, Bun S3, Cloudinary, Dropbox, Firebase, FTP, Google Drive, Netlify Blobs, OneDrive, PocketBase,
  SFTP, SharePoint, Supabase, UploadThing and Vercel Blob** store an object in one request. Send the whole file
  in one `PATCH` (or with creation-with-upload); a partial chunk is rejected with `405` instead of being stored as
  a truncated file.
- S3, GCS and Azure drop an upload's metadata once it completes, so a `HEAD` after completion answers `404`, as the
  protocol allows.

## Status Codes

| Request                                  | Status                                       |
| ---------------------------------------- | -------------------------------------------- |
| `POST` (creation, also with upload data) | `201 Created`                                |
| `PATCH` (every successful chunk)         | `204 No Content`, with `Upload-Offset`       |
| `PATCH` with a stale `Upload-Offset`     | `409 Conflict`; the upload is left untouched |
| `PATCH` with a mismatching checksum      | `460 Checksum Mismatch`                      |
| `HEAD`                                   | `200 OK`, with `Cache-Control: no-store`     |
| `DELETE`                                 | `204 No Content`                             |
| Unknown / expired upload                 | `404 Not Found` / `410 Gone`                 |
| Malformed `Upload-*` header              | `400 Bad Request`                            |

```typescript
const tus = new Tus({

        console.log("Upload complete:", file.id);
    },
    onUploadError: (error) => {
        console.error("Upload error:", error);
    },
});
```

## Resuming Uploads

TUS automatically handles resumable uploads:

```typescript
// Client checks upload status
const response = await fetch("http://localhost:3000/upload/tus/upload-id", {
    method: "HEAD",
});

const offset = response.headers.get("Upload-Offset");
const length = response.headers.get("Upload-Length");

// Resume from offset
const upload = new tus.Upload(file, {
    endpoint: "http://localhost:3000/upload/tus",
    uploadUrl: "http://localhost:3000/upload/tus/upload-id",
    // Upload will automatically resume from offset
});
```

## Best Practices

1. **Use appropriate chunk sizes** - Balance between efficiency and memory usage
2. **Handle network errors** - Implement retry logic on the client side
3. **Monitor progress** - Use HEAD requests to track upload status
4. **Clean up incomplete uploads** - Use expiration extension for automatic cleanup
5. **Verify integrity** - Use checksum extension for large files

## Comparison with REST Handler

| Feature           | TUS Handler   | REST Handler     |
| ----------------- | ------------- | ---------------- |
| Resumable         | ✅ Yes        | ✅ Yes (chunked) |
| Protocol          | TUS Protocol  | HTTP REST        |
| Client Library    | tus-js-client | Native fetch     |
| Progress Tracking | Built-in      | Custom headers   |
| Checksum Support  | ✅ Yes        | ✅ Yes           |
| Batch Operations  | ❌ No         | ✅ Yes           |

Choose TUS for:

- Standard resumable upload protocol
- Large files with unreliable networks
- Client libraries that support TUS

Choose REST for:

- Simple HTTP-based uploads
- Batch operations
- Custom upload workflows
