# Caching

vis caches the result of every task whose target is marked cacheable. On a
hit it restores the task's declared outputs and replays its recorded stdout
instead of running the command, so a warm run costs process startup and
little else.

## Where things live on disk

Two separate directories, with two separate lifecycles. You need both to
write a CI cache block, and only one of them should ever be cached.

| What                | Default location          | Config key                  | Cache it in CI? |
| ------------------- | ------------------------- | --------------------------- | --------------- |
| Task cache          | `node_modules/.cache/vis` | `taskRunner.cacheDirectory` | **Yes**         |
| Run state (`.vis/`) | `<workspaceRoot>/.vis`    | `taskRunner.dataDirectory`  | No              |

### Task cache — `node_modules/.cache/vis`

Cached task outputs and replayed logs. Safe to delete at any time; the next
run just repopulates it.

It sits under `node_modules/` deliberately: `.vis/` is **source-bearing and
tracked** (see below), so caching `.vis/` wholesale in CI would sweep
tracked files into the cache archive, and a later restore could resurrect
templates or hooks a contributor had deleted. Living under `node_modules/`
also means it is gitignored for free.

Override it with any of, in precedence order:

1. `--cache-dir` on the command line
2. `taskRunner.cacheDirectory` in `vis.config.ts` (relative paths resolve
   against the workspace root)
3. the `VIS_CACHE_DIRECTORY` environment variable

```ts
export default defineConfig({
    taskRunner: {
        cacheDirectory: ".vis-cache",
    },
});
```

`vis cache size` prints the resolved path, which is the quickest way to
confirm what is actually in effect:

```bash
$ vis cache size --type=task
Task cache:
  Directory:  /repo/node_modules/.cache/vis
  Entries:    13
  Total size: 8.5MB
```

### Run state — `.vis/`

Run summaries, failure logs, and the release/template/hook files vis reads
back. **Do not ignore or cache `.vis/` wholesale** — parts of it are meant
to be committed:

| Path                     | Tracked? | Written when                           |
| ------------------------ | -------- | -------------------------------------- |
| `.vis/templates/`        | Yes      | `vis generate` scaffolding you commit  |
| `.vis/hooks/`            | Yes      | `vis hook` git hooks you commit        |
| `.vis/release/`          | Yes      | `vis release add` change files         |
| `.vis/runs/`             | No       | every run, when `taskRunner.summarize` |
| `.vis/last-summary.json` | No       | every run                              |
| `.vis/last-failures/`    | No       | on failure                             |

`vis init` appends exactly the ephemeral three to `.gitignore`.

## Cache keys: declared and traced inputs

By default a task's cache key is built from the `inputs` you declare: the files,
env vars and runtime values you list, plus the lockfile. A file you do not list
cannot change the key.

A target can instead use `hashMode: "trace"`. vis then runs the command under its
file-access tracker and keys the cache on the files the command actually read and
the env vars it actually consulted, so no `inputs` list is needed:

```ts
export default defineConfig({
    tasks: {
        build: { hashMode: "trace" },
    },
});
```

For a single run, `vis run build --hash-mode trace` traces the requested target
(`--hash-mode declared` turns a configured trace target back off). The workspace
switch `taskRunner.autoFingerprint: true` traces every task.

How reads are observed depends on the platform:

| Platform        | Observed by                                              | What is seen                                  |
| --------------- | -------------------------------------------------------- | --------------------------------------------- |
| Linux           | `strace`, or the bundled seccomp helper                  | Every file syscall, including child processes |
| macOS / Windows | Interposition for a command run directly, no shell       | Every file access of that command             |
| macOS / Windows | Node preload for shell commands (`&&`, pipes, redirects) | Only `fs` calls made by Node processes        |

When the tracker observes no workspace access at all (for example a static binary
on a host without `strace`), what happens next depends on the target:

- **The target declares `inputs`.** The run is keyed on its declared hash, the same
  key `declared` mode uses. A later run hits as long as the declared inputs have not
  changed, and a change re-executes the task. `vis cache why` prints
  `key: declared-fallback`, and the run summary records `hashSource: "declared-fallback"`.
- **The target declares no `inputs`.** Nothing declared can key the run, so it is not
  cached. vis prints a warning instead of storing an entry under an empty key.

A traced key is a digest of the observed file hashes, the env values, and the tracker
that produced them (`seccomp`, `strace`, `interpose`, `iat` or `preload`). The same
workspace traced on two platforms therefore never shares a key.

A stored trace is also checked against the tracker the current run will use. The
tracker is predicted before the command runs, from the same host and command checks,
so a stored trace from a different tracker misses at once with
`Tracker changed (strace -> preload)` in `vis cache why`, and the run re-stores its
entry under the new tracker. The change costs one miss. Entries written by older
releases record no tracker and still hit. Declared-fallback entries are keyed on the
declared hash, which does not depend on the tracker, so they are not checked.

Traced keys can differ between machines, because the observed read set depends on
the platform. Keep targets on `"declared"` whenever you can list their inputs.

## Splitting a command chain: `splitCompound`

A target whose command is one long `&&` chain is cached as a single unit: change
the last step and every step re-runs. Set `splitCompound: true` to cache each
step on its own:

```ts
export default defineConfig({
    tasks: {
        check: {
            command: "eslint . && tsc --noEmit && vitest run --passWithNoTests",
            inputs: ["production"],
            splitCompound: true,
        },
    },
});
```

vis splits the command on top-level `&&` and runs each segment as its own task,
`check#1`, `check#2` and `check#3`. The split is visible in `vis run check --dry-run`
and in the run summary, where each segment carries its position in the chain.

- **Chained keys.** A segment's key includes the key of the segment before it,
  because an earlier step can change files or state that a later step reads. A
  change to the last step re-runs only that step. A change to the first step
  re-runs all three.
- **Failure stops the chain.** A failing segment ends the run for that target, as
  `&&` does on the command line. Later segments are neither run nor cached.
- **Output order is kept.** On a cache hit, each segment's saved output is replayed
  in chain order.
- **Forwarded arguments** (`vis run check -- --reporter dot`) go to the last segment,
  where they sit in the command line.

The split is refused, and the target runs as one unit with a warning, when:

- the command contains anything the splitter does not model: `;`, `||`, a
  background `&`, subshells `( … )`, command substitution `$( … )` or backticks,
  heredocs, `#` comments, an empty segment (`a &&`), or a shell-state change at the
  start of a segment (`cd`, `export`, `source`, `set`, `trap`, `exec`, a leading
  `VAR=value`). Quoted `&&` such as `echo "a && b"` is not a boundary and does not
  stop the split;
- the target uses `hashMode: "trace"`, or the workspace enables auto-fingerprinting;
- the workspace enables auto-fingerprinting, or the target declares an
  `{ auto: true }` output. Auto outputs come from write tracking for the whole
  target and cannot be attributed to one segment;
- the target has a `when` condition or `always`, or a custom `shell`, which runs the
  command in another language.

Declared `outputs` attach to the **last** segment, so a cache hit on the whole chain
restores them. A partial hit does not restore an earlier segment's files. If a later
segment reads a file that an earlier segment writes, it can fail on a clean checkout
after the earlier segment was cached. Put that file's producer and consumer in
separate targets, and declare the file as an output of the producer's target.

## Environment variables in the cache key

An env var enters a key only when a source names it:

| Source                              | Mode     | Effect                                                                                                                   |
| ----------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------ |
| `inputs: ["env://NAME"]`            | declared | Hashes `NAME`.                                                                                                           |
| `envVars`, `globalEnv`              | declared | Hashes the listed names for every task. Never filtered by `untrackedEnv`.                                                |
| `autoEnvVars: true`                 | declared | Hashes each `$VAR` / `${VAR}` referenced in the command text.                                                            |
| `fingerprintEnv` (target)           | both     | Hashes the names or patterns for this target.                                                                            |
| `taskRunner.fingerprintEnvPatterns` | trace    | Hashes matching vars for every traced task.                                                                              |
| `untrackedEnv` (target)             | both     | The task still receives the variables, but they stay out of the key. Wins over the other implicit sources.               |
| `taskRunner.untrackedEnvVars`       | both     | Workspace-wide untracked list. The built-in CI defaults (`CI_*`, `GITHUB_*`, `BUILDKITE_*`, …) apply to trace-mode keys. |

A name the command reads that no source above covers can serve a stale result.
`vis doctor` lists those names per target, with the source to add. See
[Env Coverage](/commands/doctor#env-coverage).

Patterns accept `*` anywhere in the name, for example `VITE_*`, `*_TOKEN` or
`AWS_*_KEY`:

```ts
export default defineConfig({
    tasks: {
        build: {
            hashMode: "trace",
            fingerprintEnv: ["NEXT_PUBLIC_*"],
            untrackedEnv: ["NEXT_PUBLIC_BUILD_ID"],
        },
    },
});
```

## Clean child environment

A task's cache key should change when the task's output can change. A
variable the task never receives cannot change its output, so vis does not let
it bust the key. This applies when a task runs with `taskRunner.env` (or its
own `options.env`) in `clean` mode, which is described in
[`vis run`](/commands/run#clean-child-environment):

- A name the clean child cannot see hashes as unset, in every source that
  names it: `envVars`, `fingerprintEnv`, `autoEnvVars` and `env://` inputs.
  Changing its value does not bust the key.
- `globalEnv` is shared by every task in a run, so a name is hidden from its
  key only when no task in the run can see it. One target that inherits the
  parent environment keeps the name in the shared key.
- A name the clean child can see is keyed as usual.
- Allow-listing a name does not add it to the key. Add it to `fingerprintEnv`
  (or `envVars`) when its value should bust the key.

For example, in `project.json`, only the allow-listed `DATABASE_URL` reaches the
child, and it is in the key:

```json
{
    "targets": {
        "migrate": {
            "command": "node migrate.js",
            "fingerprintEnv": ["DATABASE_URL"],
            "options": { "env": { "mode": "clean", "allow": ["DATABASE_URL"] } }
        }
    }
}
```

A traced target (`hashMode: "trace"`, or a workspace `autoFingerprint`) can be
`clean` too. It gets the same environment as any other task, and its key covers
only the names its clean child can see, as above. The tracker runs without its
native backends in this case, so a command that is not a Node process may record
no file accesses; vis then skips caching it with a warning. For such a command use
declared hashing, or set `{ "mode": "inherit" }`.

## Making the cache work in CI

The task cache only pays off if the CI job can both **read and write** it.
Two things go wrong most often.

### The cache directory must be writable

If the job restores `node_modules` from a read-only or pull-only cache, the
default cache directory lives inside it and everything vis writes is
discarded when the job ends — caching appears to work locally and never hits
in CI. Point the cache somewhere the job owns:

```ts
export default defineConfig({
    taskRunner: {
        cacheDirectory: ".vis-cache",
    },
});
```

then cache that directory instead.

### The cache must be keyed so parallel jobs don't clobber each other

#### GitHub Actions

```yaml
- name: Cache vis task results
  uses: actions/cache@v4
  with:
      path: node_modules/.cache/vis
      key: vis-${{ runner.os }}-${{ github.job }}-${{ github.sha }}
      restore-keys: |
          vis-${{ runner.os }}-${{ github.job }}-
          vis-${{ runner.os }}-
```

#### GitLab CI

GitLab's cache is per-key and last-writer-wins, so give each job its own key
and fall back to the default branch's archive. Without a per-job key,
concurrent jobs overwrite each other's archive and every job starts cold.

```yaml
cache:
    - key: "$CI_JOB_NAME_SLUG-$CI_COMMIT_REF_SLUG-vis"
      fallback_keys: ["$CI_JOB_NAME_SLUG-$CI_DEFAULT_BRANCH-vis"]
      paths: [.vis-cache]
      policy: pull-push
```

This pairs with `taskRunner.cacheDirectory: ".vis-cache"` above. If you keep
the default cache directory, cache `node_modules/.cache/vis` instead — but
only when the job actually pushes its `node_modules` cache back.

## Collapsing jobs is usually the bigger win

Caching removes the task work; it does not remove the per-job scaffolding
(runner start-up, checkout, dependency restore) that a matrix of separate
jobs pays once each. A single job running one graph lets vis overlap
independent targets, and pays that fixed cost once:

```yaml
script:
    - pnpm vis ci lint,test,build
```

See [`vis ci`](/commands/ci) and the [CI/CD guide](/guides/ci-cd).

## Inspecting and debugging the cache

| Command                   | Use it to                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `vis cache size`          | Confirm the resolved directory and on-disk footprint                                                               |
| `vis cache list`          | See individual entries with age and size                                                                           |
| `vis cache why <task>`    | Explain a miss: diff declared inputs against the previous run, or print the recorded miss reasons of a traced task |
| `vis cache hash <task>`   | Print the recorded hash and its per-bucket breakdown, or the files and env a traced run tracked                    |
| `vis cache verify <task>` | Detect drift between the cached entry and the live workspace                                                       |
| `vis cache prune`         | Evict by age, size, or count                                                                                       |
| `vis cache clean`         | Clear everything                                                                                                   |

`vis cache why` and `vis cache hash` read `.vis/last-summary.json`, which every
run writes. Diffing against an older run (`--run <id>`) needs the historical
summary in `.vis/runs/`, written by `--summarize` or `taskRunner.summarize`.

For a traced task, a miss records why it missed (for example `File modified:
src/a.ts`), and `vis cache hash` lists the files, env var names and missing paths
the run tracked. Set `taskRunner.cacheDiagnostics: true` to also fire the `task:cacheMiss`
plugin hook with the same reasons as each miss happens.
