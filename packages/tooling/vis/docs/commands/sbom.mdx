# vis sbom

Generates a CycloneDX 1.7 Software Bill of Materials (SBOM) for the current workspace, capturing every workspace project, every reachable registry dependency, per-version licenses, and the dependency graph.

The generator walks the workspace project graph plus the lockfile closure, so the emitted BOM includes both direct and transitive dependencies — the same closure that is actually installed in `node_modules`.

## Usage

```bash
vis sbom [options]
```

## Examples

```bash
# Full-workspace SBOM → sbom.cdx.json
vis sbom

# Scope to a single project's closure
vis sbom --focus=my-app

# Focus multiple projects
vis sbom --focus=my-app,other-app

# XML output
vis sbom --format=xml --output=sbom.cdx.xml

# Include devDependencies
vis sbom --include-dev

# Write to stdout (for piping / CI)
vis sbom --output=-
```

## Options

| Option          | Default         | Description                                                                                       |
| --------------- | --------------- | ------------------------------------------------------------------------------------------------- |
| `--focus`       |                 | Project name(s) to focus on — comma-separated. Scopes the BOM to the transitive closure.          |
| `--format`      | `json`          | Output format: `json` (CycloneDX 1.7 JSON) or `xml`.                                              |
| `--output`      | `sbom.cdx.json` | Output file path (resolved against the workspace root). Use `-` to write to stdout.               |
| `--include-dev` | `false`         | Include `devDependencies` in the closure walk. Default is production-only, per industry practice. |

## What's in the BOM

Every emitted BOM passes the vendored CycloneDX 1.7 JSON Schema (`bom-1.7.schema.json`). Each `components[]` entry carries:

- `name` + `version` + `purl` (`pkg:npm/…` Package URL)
- `bom-ref` (unique per component)
- `type: "library"` (or `"application"` for the workspace root / focus target)
- `scope: "required" | "optional"` — `optional` propagates only through `optionalDependencies` edges; `required` wins on any shared path
- `hashes: [{ alg, content }]` — decoded from SRI when the lockfile provides one
- `licenses` — resolved against the specific installed `node_modules/.pnpm/<name>@<version>/` copy so different versions can carry different licenses
- `description`, `author`, `externalReferences` (`homepage`, `vcs`, `issue-tracker`) from the installed copy

`dependencies[]` edges cover both workspace project → project edges and registry → registry edges (from the lockfile graph walk).

## Package manager support

| Package manager | Lockfile                      | SBOM coverage                                                                                                                                                                                                                                     |
| --------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pnpm            | `pnpm-lock.yaml`              | ✅ Full                                                                                                                                                                                                                                           |
| npm             | `package-lock.json` (v2 / v3) | ✅ Full                                                                                                                                                                                                                                           |
| Yarn Classic    | `yarn.lock` (v1)              | ✅ Full                                                                                                                                                                                                                                           |
| Yarn Berry      | `yarn.lock` (v2+)             | ✅ Full except integrity hashes — Berry uses XXH64 (`checksum:`), which is not a cryptographic hash and is outside CycloneDX 1.7's `HashAlgorithm` enum. Berry components emit without a `hashes` entry; all other fields are populated normally. |
| Bun             | `bun.lock` (1.1+)             | ✅ Full                                                                                                                                                                                                                                           |

Binary `bun.lockb` is not supported.

## Zig packages

`vis sbom` lists the `.dependencies` of a Zig workspace's `build.zig.zon` and of its in-workspace `.path` packages, as a flat list with no edges. Zig's manifest records no dependency versions, so a version is set only for a dependency whose `.url` is a git tag archive (`refs/tags/<tag>`). Other dependencies are listed without a version and say so in a `vis:zig:version` property. Nothing is invented. The audit cannot check Zig packages at all; see `vis audit`.

## Rust and Python lockfiles

The BOM also includes `Cargo.lock` (Rust) and `uv.lock` (Python) when they exist at the workspace root. Each locked package becomes a component with a `pkg:cargo/…` or `pkg:pypi/…` purl, and dependency edges come from the lockfile graph.

What is kept follows the same rules as the npm closure:

- Only packages reachable from the workspace members are included. With `--focus`, the walk starts from the focused projects that are Cargo or uv projects.
- Dev dependencies are left out unless `--include-dev` is set. For Cargo, dev-dependencies are read from each member's `Cargo.toml`, because the lockfile merges them with normal dependencies. For uv, dependency groups are read from their own section. uv extras are always kept, like optional npm dependencies.
- When two packages share a name and version but come from different sources, every one of them that has a source gets a `?source=` qualifier on its `bom-ref` and `purl`, so they stay distinct. An entry without a source, such as the Cargo workspace entry, keeps the plain purl.

Without a lockfile, these ecosystems add nothing to the BOM.

## Opt-in ecosystems

Eight ecosystems are left out of the BOM unless you opt in: Maven, Gradle, Hex, Go, Dart, Swift, NuGet and Zig. Each one is included when its discover key is on (`maven.discover`, `gradle.discover`, `hex.discover`, `go.discover`, `dart.discover`, `swift.discover`, `nuget.discover`, `zig.discover` in `vis.config.ts`), or when it is listed in `sbom.ecosystems`:

```ts
sbom: {
    ecosystems: ["go", "zig"];
}
```

A lock file or manifest on its own does not include an ecosystem. When one is found but not opted in, `vis sbom` prints a single line on stderr naming the file and the key that would include it, for example `go.sum found; not included. Set go.discover or add 'go' to sbom.ecosystems.` The BOM itself is unchanged by that notice.

`--focus` narrows Maven to the focused modules. The other opted-in ecosystems are flat lists: Gradle, Go, Dart, Swift and Zig have no dependency edges in their lock files, and Hex and NuGet name no workspace projects, so focus does not apply to them.

## Focus mode

`--focus=<project>` scopes the BOM to one or more workspace projects plus their transitive closure. The focused project becomes `metadata.component`; other workspace projects outside the closure are excluded.

Useful for Docker images, deploy artifacts, or per-app compliance reports:

```bash
vis sbom --focus=web-app --output=dist/web-app/sbom.cdx.json
```

## Limitations

- **License lookup is best-effort**. The generator resolves each `name@version`'s license against its installed `package.json` — trying pnpm's virtual store (`node_modules/.pnpm/<name>@<version>/node_modules/<name>/package.json`, including peer-disambiguated suffixes) first, then the hoisted `node_modules/<name>/package.json` (version-matched). npm's nested `node_modules/parent/node_modules/<pkg>/` layouts and Yarn PnP are not searched; components whose installed copy isn't found emit without license decoration rather than failing.
- **Yarn Berry integrity** is dropped (XXH64 is not a supported algorithm). See the matrix above.

## Why

Regulatory mandates for SBOMs include:

- **US Executive Order 14028** (2021) — federal supply-chain security
- **EU Cyber Resilience Act** — effective December 2027
- **PCI DSS 4.0** — payment-card industry compliance

`vis sbom` is designed to be the first monorepo-native CycloneDX generator — moon, Nx, and Turborepo do not emit SBOMs out of the box. `cdxgen` exists but is heavy (200+ dependencies) and not monorepo-aware.

## Configuration

No `vis.config.ts` configuration is required. The command reads directly from the workspace lockfile + `package.json` files.
